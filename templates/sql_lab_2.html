1. Search Box (code vs data)

The search box pastes your text straight into the query. It builds this SQL: 

SELECT id, name, price FROM products WHERE name LIKE '%<your input>%'
Why did the whole table come back? Because the OR 1=1 was executed as code, and -- commented out the closing %'.
2. URL Parameter (numeric)

A product page reads id from the URL and builds this query - no quotes needed: 

SELECT * FROM products WHERE id = <your input>
A numeric parameter is injected without any quotes - the digit is just replaced by whatever the attacker types.
3. The Comment Trick

Legitimate pages often add a trailing condition, such as AND active = 1 or -- check password. The two dashes -- comment out everything after them: 

SELECT * FROM users WHERE username = '<input>' AND password = '<input>'

Without -- (password still checked)

username =  admin'
AND password =  'x
SELECT * FROM users WHERE username = 'admin' AND password = 'x'

With -- the rest disappears

username =  admin'--      
AND password =  'whatever'
SELECT * FROM users WHERE username = 'admin'-- ' AND password = 'x'
The part after -- is still sent to the server, but the database never reads it - it becomes a comment. That is how an attacker disables the password check.
4. The Fix: Parameterized Queries

VULNERABLE (string concatenation)

product = input("Search: ")
query = "SELECT * FROM products WHERE name LIKE '%" + product + "%'"
cursor.execute(query)
The payload becomes part of the SQL itself.

SAFE (parameterized / prepared statement)

product = input("Search: ")
query = "SELECT * FROM products WHERE name LIKE ?"
cursor.execute(query, ("%" + product + "%",))
The payload stays plain text - it can never change the SQL.
